# StayClean スプリント2 ユーザーシナリオ（実機テスト用・網羅版 v2）

- 作成日: 2026-06-21 / v2: Codexレビュー反映済
- 目的: 本番（`https://minpaku-cleaning.vercel.app`）に対する実機テストのためのユーザーシナリオ網羅。
- **作成方針**: 実装コードは見ず、**設計書（`docs/2026-05-14-design-client.md`）＋スプリント2改修要件（`~/.claude/plans/stay-clean-2-groovy-tide.md`）＋Sprint1検収（`handoff/client-facing/04-acceptance-test.md`）** のみを根拠に、期待挙動を要件側から定義する。
- 対象ロール: 管理者（要ログイン）／清掃スタッフ（専用URL）／物件オーナー（専用URL・閲覧）／システム（cron・通知）
- 凡例: 種別 = 正常 / 異常 / 境界 / 権限 / 回帰。実行区分 = 【公開】ログイン不要で本番確認可 / 【要管理者】管理者ログイン要 / 【要LINE】実LINEトークン要 / 【要API/別環境】ブラウザ実機では再現困難（API直叩き/ステージング/ログ確認）

## 0. 前提・テストデータ規約

- 本番DBへテストデータを投入する。識別のため命名接頭辞 `E2E-`。テスト後クリーンアップ対象。
- **実行日を冒頭に固定記録**し、各シナリオの相対日（当日/翌日/2日後）を**絶対日付＋JST時刻**で併記して判定ブレを防ぐ。
- 実メール/実LINE送信が発生しうる。宛先はテスト用に限定。
- 同時実行（先着・TOCTOU）検証は2ブラウザ（or 2タブ＋別トークン）。
- 未解決の要件差分（テスト前に確定要）:
  - **【OPEN-1】未確定アラートの宛先**: 設計書=「管理者・物件オーナー」／Sprint2計画=「管理者アラート」。Sprint2でオーナー宛を廃止したのか要確定。本書は暫定で「管理者（＋設計書準拠ならオーナーも）」と記載。
  - **【OPEN-2】cron実行基盤**: Sprint2計画は `vercel.json` cron だが、その後 sub-daily（ical-sync/finalize-offers）を**Supabase Cron へ移行**済み。実機では実周期をログで確認。

## グループP0. CRUD不具合修正

### S-P0-1【回帰・正常】オーナー編集 — 【要管理者】
- 前提: `E2E-オーナーA`（メール登録済）。
- 手順: オーナー詳細→名前/メール変更→保存→再読込。
- 期待: 保存成功、一覧・詳細に反映、再読込後も保持。

### S-P0-2【正常】オーナー削除（紐づく物件なし）— 【要管理者】
- 前提: 物件が紐づかない`E2E-オーナー削除用`。
- 手順: 削除。
- 期待: 削除成功、一覧から消える。

### S-P0-3【異常・FK保護/409】物件紐づきオーナーの削除ブロック — 【要管理者】
- 前提: `E2E-オーナーA`に`E2E-物件A`が紐づく。
- 手順: `E2E-オーナーA`を削除。
- 期待: **API/HTTPは409相当**。画面は「紐づく物件があり削除不可」の文言。**DB生エラー/500は出ない**。物件・オーナーとも不変（cascadeしない）。

### S-P0-4【境界・バグ回帰】物件のオーナー変更が保存される — 【要管理者】
- 前提: `E2E-物件A`がオーナーA。別`E2E-オーナーB`用意。
- 手順: 物件Aのオーナーを B に変更→保存→再読込。
- 期待: オーナーが B に**確実に保存**（旧バグ: update時 owner_id 無視が再発しない）。

### S-P0-5【正常】スタッフ自己編集 — 【要管理者(URL発行)】＋【公開(スタッフURL)】
- 前提: `E2E-スタッフX`の専用URL発行済み。
- 手順: スタッフ用URL→プロフィール画面でメール変更→保存。LINEは**手入力ではなく**「LINE連携」ボタンから `/api/line/link/start` へ進む導線。
- 期待: **メールは本人が保存可**、管理画面にも反映。**LINEは手入力欄ではなくLINE Login導線**（bindはOAuth完了後・S-P4参照）。

### S-P0-6【権限・IDOR防止】スタッフは他人のプロフィールを編集不可 — 【要API】
- 前提: スタッフX・Y。
- 手順: Xのトークンで Y（別staff_id）のメール更新をAPIで試行。
- 期待: 拒否（本人staff_idのみ可）。Y不変。

### S-P0-7【正常】トークン自動発行 — 【要管理者】
- 手順: 新規スタッフ作成→詳細を開く / 新規物件作成→詳細を開く。
- 期待: 作成時点で専用URLトークンが**自動発行済み**（手動「発行」不要）。オーナーURLは物件単位。

### S-P0-8a【正常】スタッフURL再発行・無効化 — 【要管理者】
- 手順: スタッフ詳細でトークン再発行→旧URLを開く。さらに無効化→新URLを開く。
- 期待: 再発行後は旧URL不可・新URL可。無効化後は**新旧とも不可**。

### S-P0-8b【正常】物件オーナーURL再発行・無効化 — 【要管理者】
- 手順: 物件詳細でオーナーURLを再発行→旧URL確認、無効化→確認。
- 期待: 再発行後は旧不可・新可。無効化後は新旧とも不可。

## グループP1. 通知テンプレ刷新（文面・予定リスト埋込）

### S-P1-1【正常】依頼通知に清掃予定リスト埋込 — 【要管理者】＋通知受信確認
- 前提（具体）: `E2E-物件A`に当月「6/25 依頼中」「6/28 確定済(田中さん)」、翌月「7/3 人数変更」「7/10 キャンセル」を作る。
- 手順: 新規依頼作成→スタッフ宛通知発生。
- 期待: 本文に今月・来月見出し付きの予定リスト。行頭マーカー: 依頼中=🆕 / 人数変更=🔺 / キャンセル=❌、確定済=「(6/28 田中さん清掃予定)」付記。サンプル期待行を実物と突合。

### S-P1-2【境界】月跨ぎ・空状態 — 【要管理者】
- 手順: 予定が翌月のみ／予定ゼロの物件で依頼通知。
- 期待: 当月空でも崩れず「予定なし」相当を表示。月見出しが正しい。空状態文言が出る。

### S-P1-3【正常】新kind文面の必須項目 — 【要管理者】＋受信確認
- 各kindで以下の必須項目が揃うことを確認:
  - clean_confirmed（確定）: 物件名・清掃日・人数・シフトURL
  - clean_passed_over（見送り）: 物件名・清掃日・見送りである旨
  - request_changed（変更）: 物件名・変更点（特に人数🔺）・対象清掃日
  - request_cancelled（キャンセル）: 物件名・対象清掃日・キャンセルである旨
  - new_reservation_alert（新規予約アラート）: 物件名・新予約日・既存確定との競合内容

### S-P1-4【設定】kind別LINE可否フラグ — 実行区分の切分
- 管理者UIで切替可能なら【要管理者】で実機。環境変数/設定ファイル制御なら本番実機では確認不能→【要API/別環境】（ログ/設定で確認）。どちらかを実機で判定し記録。

## グループP2. iCal予約取込

### S-P2-1/S-P2-2【正常・境界TZ】固定fixtureで取込＋JST日付 — 【要管理者】＋【要API/cron】
- 固定fixture例: `DTSTART;VALUE=DATE:20260625` / `DTEND;VALUE=DATE:20260627`。
- 手順: 物件詳細でこのiCal URLを登録→ical-sync発火。
- 期待: 取込予約 checkin=`2026-06-25`、checkout=`2026-06-27`（**終日VEVENTのUTC解釈による前後日ズレが無い**）。

### S-P2-3【異常】不正VEVENT破棄 — 【要API/cron】
- 前提: 日付欠損・壊れ行を含むフィード。
- 期待: 不正分スキップ、正常分のみ取込、全体failにしない。

### S-P2-4【境界】人数手動補完が再取込で非破壊 — 【要管理者】＋【要cron】
- 手順: 取込後に管理者が宿泊人数を手入力→再度ical-sync。
- 期待: **手入力人数が消えない**（guest_count非破壊upsert）。

### S-P2-5【正常】キャンセル検知 — 【要cron】
- 手順: あるexternal_uidを次回フィードから消す→ical-sync。
- 期待: 該当予約 status=cancelled。確定済み清掃が紐づけば担当スタッフへキャンセル通知。

### S-P2-6【境界】複数OTAのUID衝突分離 — 【要API/cron】
- 前提: feed A/B に同一external_uid。
- 期待: `(feed_id, external_uid)`で別予約として保持（取り違えない）。

### S-P2-6b【境界】feed単位のキャンセル分離 — 【要API/cron】
- 手順: 同一UIDを持つ feed A/B のうち **A からだけ** 該当UIDを消す→ical-sync。
- 期待: **A側のみ cancelled、B側は active 維持**（feedスコープでcancel判定）。

### S-P2-7【正常】新予約が既存確定清掃日より前 → アラート — 【要cron】
- 手順: 確定済み清掃予定日より前のcheckoutを持つ新予約を取込。
- 期待: 管理者＋担当清掃員へアラート。

### S-P2-8【権限・SSRF】内部アドレス拒否（登録時/取込時を分離）— 【要API】
- 個別ケース: `http://127.0.0.1` / `http://169.254.169.254` / private IP（10/172.16/192.168）/ 公開URL→内部へ302リダイレクト / DNS解決後がprivate IP。
- 期待: **登録時**または**取込時**に各ケース拒否。内部リソースへ到達しない。

### S-P2-9【正常】取込予約から依頼作成（中核導線）— 【要管理者】
- 前提: S-P2-1で取込済み予約。
- 手順: 管理画面で取込済み予約を選び依頼作成へ。
- 期待: checkin/checkout/guest_count/reservation_id が**プリフィル**。**予約から依頼は自動生成されず手動作成**。offer_date_start=checkout、offer_date_end=min(次checkin, checkout+3)。

## グループP3. 複数人依頼→回答→確定アルゴリズム（中核）

### S-P3-1【正常】複数スタッフ送信＋除外 — 【要管理者】
- 前提: 物件A担当=X,Y,Z。
- 手順: 依頼作成で送信先一覧を確認、Zを除外して作成。
- 期待: X,Yへ通知、Zには来ない。recipientsに除外フラグ記録。

### S-P3-2【正常・先着即確定】当日(offset0)回答の先着確定 — 【公開(スタッフURL)】
- 前提: 有効清掃日=[checkout, min(次checkin,+3)]。当日offset0回答可。
- 手順: Xがoffset0（checkout当日）で「対応可」。
- 期待: **即確定**。Xへ「清掃確定」、他のavailable回答者へ「見送り」。assigned_staff_id=X。

### S-P3-3【正常・暫定待ち】offset>0は24h暫定 — 【公開】
- 手順: 当日回答無しでYがoffset1（翌日）「対応可」。
- 期待: 即確定せず暫定。最初の暫定回答時刻+24hを provisional_decision_at にセット。

### S-P3-4【正常・当日優先】24h以内に当日回答→当日優先 — 【公開】
- 前提: S-P3-3の暫定状態。
- 手順: 24h以内にXがoffset0「対応可」。
- 期待: 当日優先で確定（暫定Yは見送り）。

### S-P3-5【正常・cron確定】24h経過後にcronが最早日付確定 — 【要cron】
- 前提: 暫定のみ・当日回答なしで provisional_decision_at 経過。
- 手順: finalize-offers cron発火。
- 期待: 最早日付（同日なら先着）を確定。**deadline経過後、次回cron実行から最大10分以内**に反映。確定/見送り通知。

### S-P3-6【異常・全員不可】全員「対応不可」で管理者アラート — 【公開＋要cron】
- 手順: X,Y,Z全員「対応不可」。
- 期待: 確定されず管理者アラート（自動キャンセルしない）。

### S-P3-7【異常・期限切れ未確定】依頼後24h未確定で管理者アラート — 【要cron】
- 手順: 誰も回答せず assignment_deadline（依頼後24h）経過→cron。
- 期待: 管理者アラート（【OPEN-1】設計書準拠ならオーナーも）。次回cronから最大10分以内。

### S-P3-8【境界・TOCTOU】同時確定の単一勝者保証 — 【公開・2タブ】
- 手順: 2タブで2名がほぼ同時にoffset0「対応可」。
- 期待: 確定は**1名のみ**、もう一方は見送り/失敗。二重assignにならない（WHERE status='unassigned'）。

### S-P3-9【境界】1依頼1回答（後勝ちupsert）— 【公開】
- 前提: **他スタッフ未回答・全員不可条件が未成立**の状態。
- 手順: Xが「対応不可」→後で「対応可」に回答し直す。
- 期待: 最新回答（可）が有効。重複レコード増えない。（アラート後の再回答可否は別途）

### S-P3-10【正常・確定後動線/回帰】確定者がシフトURLから清掃実施 — 【公開】
- 手順: 確定通知のシフトURL→清掃開始→完了報告（チェックリスト全項目＋**写真2枚必須**）→管理者確認済み。
- 期待: assigned→in_progress→reported→confirmed の既存機械が無改造で動く。**写真0/1枚は拒否、2枚で成功**。

### S-P3-11【正常】人数変更（手動編集）の通知 — 【要管理者】
- 手順: 確定済み依頼の宿泊人数を管理者が変更。
- 期待: 担当スタッフへ「依頼変更（🔺人数変更）」通知。

### S-P3-12【正常】依頼キャンセルの通知 — 【要管理者】
- 手順: 確定済み依頼を手動キャンセル。
- 期待: 担当スタッフへキャンセル通知。予定リストで❌表記。

### S-P3-13【境界】有効清掃日ウィンドウ算出 — 【要管理者】
- ケース: ①次checkinが**同日** → ウィンドウ=checkout当日のみ。②次checkinが**2日後** → [checkout, +2]。③次checkinが**3日後** → [checkout, +3]。④次checkinが**5日後** → [checkout, +3]頭打ち。⑤**次checkinなし** → [checkout, +3]。
- 期待: 各ケースでoffer_date_end=min(次checkin, checkout+3)。

### S-P3-14【権限・回答境界】回答できない主体の拒否 — 【要API】
- 手順: 除外済みZ / 担当外スタッフ / 別物件スタッフ / オーナーURL で回答API/画面操作。
- 期待: いずれも拒否、responseが作られない、確定が走らない。

### S-P3-15【境界・回答日範囲外】offered_dateがウィンドウ外は拒否 — 【公開/要API】
- 手順: checkout前の日付、offer_date_end翌日 を回答として選ぶ/送る。
- 期待: 拒否、responseが作られず確定も走らない。
